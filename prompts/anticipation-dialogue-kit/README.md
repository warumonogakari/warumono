# anticipation-dialogue-kit

「読む未来語りのダイアローグ」——組織の膠着を、{N}年後の未来から全員の一人称で
ふりかえるシナリオを、**複数のAIエージェントに配役として演じさせて**生成するための
プロンプトセットです。

## 未来語りのダイアローグとは

フィンランドで開発された対話手法 Anticipation Dialogue（未来語りのダイアローグ）を
下敷きにしています。心配事を抱えた依頼者が場を持ち込み、参加者全員が「{N}年後の
良い状態の未来」に飛んで、そこから今日までに起きたことを**過去形で**語る——
解決やまとめを目指さず、一人一人の声を聴くことに徹する対話です。

このキットは、対話手法を紹介・学習するための架空事例を、破綻なく、かつ登場人物の声が
書き分けられたシナリオの形で生成します。

## なぜ配役エージェントを分けるのか

1つのモデルに全員分を一括で書かせると、作者視点の「全知」が漏れます——
まだ明かされていない秘密を別の登場人物が先取りする、未来の台詞を創作する、
全員が同じ語彙で内省する。一方、ルールで縛ると、作者視点の「全知」漏れはなくなるものの、
今度は各パートの声が予定調和になって、多様な声が出なくなりがちです。

このキットでは、**登場人物1人につきエージェント1体**を起動します。

- エージェントには、公開情報と本人のシートを**起動時に本文として渡し切る**
- 他人のシートとシステム図は、**中身も在り処も教えない**
- 加えて `agent_rules.md` で「**逐語録以外のファイルを読まない**」ことを明文で禁じる

渡さないものは知らないことになるので、秘密の先取りが起こりにくくなります。
さらにシートに空白を残した配役は細部を自己発明するため、
作者（あなた）も知らない展開が生まれます。

**空白は「薄く書くこと」ではありません。** 実際に効くのは、
**具体性の高い実感を2〜3個と、見るくせ・言うくせ・話し方を全員に渡したうえで**、
経歴や性格を空けておくことです。ここを取り違えて情報を減らすだけにすると、
配役は肩書きから人物を発明しがちになります。

トークン消費の目安: 配役合計 約400k〜500k＋メインセッション1つ分（7配役・Sonnetクラスの場合）。

## 構成

```
templates/                     # ケース非依存。そのまま使う
├── agent_rules.md             # 配役エージェントに渡すルール（書き換え不要）
├── facilitation_guide.md      # 演出兼ファシリテーター（以下、単に演出家とよぶ）の進行手順・質問セット
├── system_map_template.md     # 膠着の構図の設計テンプレート（配役には見せない）
├── public_context_template.md # 全員が知っている情報のテンプレート
├── sheet_template.md          # 内面シートのテンプレート（見るくせ・言うくせ／書き込み量3段階）
├── test_checklist.md          # 生成後の機械テスト（V1〜V7・S1〜S3）と局所修復の原則
└── review_loop.md             # レビュー指摘を`grounding_notes.md`に昇格させるための学習ループプロンプト

example_manufacturing/         # 記入例: 伝統的製造業・大部屋開発ケース（三倉製作所編）
├── system_map.md
├── public_context.md
└── sheets/                    # 配役7枚（フル/核のみ/ほぼ白紙の書き込み量の例）

HOWTO.md                       # ケースの作り方と実行手順
```

## 使い方（概要）

1. `HOWTO.md` に従い、`templates/` を埋めて自分のケース（システム図・公開情報・
   内面シート）を作る。`example_manufacturing/` が記入例
2. メインセッション（演出家）が `facilitation_guide.md` の手順で配役エージェントを
   起動し、ターン制で対話を進行。発話は逐語録に追記していく
3. 生成後、`test_checklist.md` でテストし、テストの結果、不自然な表現があれば局所修復
4. 逐語録を**朗読台本**に転写する（`facilitation_guide.md` §6）。
   参加者が役を分担して声に出して読むための脚本形式。事実・誰が何をしたか・
   発言順は変更しない
5. シナリオをレビューし、指摘をLLMに反映させる。指摘の傾向は`grounding_notes.md`に
   蓄積され、次のrunからポリフォニーがあなたの現場に接地していく
   （`templates/review_loop.md`）

## 設計上の要点

- **ポリフォニーの方針は明文化したままにしておく**: 単一の答えに収束させない・迎合しない・
  矛盾する感情と不確実性をそのまま語る・相互的情緒的同調は演出せず湧き上がらせる。
  方針文の本体は `facilitation_guide.md` 冒頭（演出家向け）と `agent_rules.md` 7
  （配役向け）にある
- **二層構造**: 演出家だけがシステム図（膠着の全体像）を見る。配役は自分の
  シートしか見ない。この情報の非対称が、整合性と意外性の両方の源泉
- **台本化しない**: 誰がいつ何を明かすか、涙、和解の形は決めない。
  決めたくなったら `system_map` の「台本化しない要素」に書いておく
- **質問の構造を潰さない**: チーム内9問・支援者4問・最後の質問（`facilitation_guide.md`）。
  全員同型の1問に潰すと語りが単調になる
- **板書確認**: 語りのブロックごとに、サブファシリが本人に板書を確認する。
  言葉の所有権を本人に返す安全装置であり、ポリフォニーの追加機会であり、
  **演出家の要約バイアスを本人が訂正する装置**でもある——
  要約する側は無意識に「角の立つ一行」を落とす
- **身体・表情・場を拾う**: 演出家は配役の身体・表情・動きを描写しない。
  身体は**開幕と{N}年後の2回、本人から取る**。それ以外で周囲の反応が要ると感じたら、
  **A層で場に問いかける**——問われた人が自分で身体を返す。演出家が書かない
- **ファシリの発言は定型文に固定する**: 質問も板書確認も、
  読み上げる文面が `facilitation_guide.md` §2 に固定されており、埋めるのは穴だけ。
  演出家がその場で言葉を選べる限り、**どの語を拾うか・いつ誰に振るかという形で
  作家性が漏れる**
