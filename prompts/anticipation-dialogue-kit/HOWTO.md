# HOWTO — ケースの作り方と実行手順

## 1. ケースを作る（30〜60分）

作る順番が大事です。**公開情報 → システム図 → シート**の順で書くと、
「全員が知っていること」と「本人しか知らないこと」の線引きがぶれません。

1. **公開情報** (`public_context_template.md` を埋める)
   - 組織・製品・外部環境・会の約束事。一人でも知らないことは書かない
   - 主人公の異変は「うすうす皆が気づいている範囲」だけをここに書く
2. **システム図** (`system_map_template.md` を埋める)
   - 役割ごとの維持行動を一行ずつ。全員が善意で、構図が噛み合って膠着していること
   - 「台本化しない要素」を明示的に列挙する（シナリオを書いていて
     決めたくなる気持ちが湧いたら、一旦ここに書いておく）
   - シートの書き込み量に差をつける: くわしく書く人2〜3人・核となる実感だけを
     書く人数人・ほぼ白紙の人1人が目安。
     差をつける目的は「発明の余地を作ること」であって、「情報を減らすこと」ではない
3. **内面シート** (`sheet_template.md` に従い1人1枚)
   - 「あなたの見るくせ・言うくせ」を全員に入れる——その人が場面を見るとき
     つい目が行くもの（例: 営業なら相手の声のトーン、設計者なら図面の構図）と、
     言葉に詰まったときつい語ってしまう比喩の出どころ（例: 営業なら検収や値引き、
     設計者なら公差やバリ取り）。これがないと、全員が同じ内省的な語り方になりがち
   - 「まだ言葉になっていない声」は半分だけ書く
   - 「あなたが知らないこと」を必ず書く（構造的な情報隠蔽の要）

## 2. 実行する

必要なもの: サブエージェント（または複数チャット）を起動でき、メインセッションから
メッセージを送れる環境。Claude Code の Agent/SendMessage、または手動で
複数チャットを並走させても再現できます。

1. メインセッション（＝演出家。あなたが操作する）に読み込ませる:
   `system_map.md`・`public_context.md`・`facilitation_guide.md`・`test_checklist.md`
2. 配役エージェントを1人1体起動。**起動プロンプトの雛形は
   `facilitation_guide.md` §0-1** にある（`public_context.md`＋**本人の**シート＋
   `agent_rules.md` を本文に貼り、逐語録だけ所在を教える形）
   - モデルは Sonnet クラスで足りる（実測）
   - **他人のシートとシステム図は、中身も在り処も教えない**
   - 逐語録は他に何も置かないディレクトリに単独で置く
   - 応答しなくなったら同じ指示を再送。駄目なら同じ起動プロンプトで起動し直す
     （逐語録が外にあるので文脈は復元できる）
3. **開幕**: ファシリが喋る前に、全配役から身体の《ト書き》を取って逐語録の冒頭に置く
   （文面は `facilitation_guide.md` §2-2）。
   配役どうしの観察材料になり、以後の語りで拾われる
4. `facilitation_guide.md` の骨格に沿って進行:
   - ファシリの台詞は `facilitation_guide.md` §2 の**定型文をそのまま読み上げる**。
     演出家がその場で言い回しを作らない
   - 配役の発話は、逐語録（それまでの全発話）を添えて本人のエージェントに
     ターンを回し、返ってきたものをそのまま使う（**演出家が創作しない**）
   - 想起はチーム内メンバー3ターン・支援者2ターン。分割点は固定
   - 発話が確定するたび `transcript.md` に追記。**追記完了を確認してからターンを送る**
   - 各語りブロックの末尾: サブファシリの板書確認ターン（→ `facilitation_guide.md` §3）
   - **周囲の身体は、開幕と {N}年後の2回、本人から取る**（§1-0・§1-4b）
   - **A層の問いかけ（A-0）は場に投げる。**全員に振らず、答えた人の発話だけが逐語録に残る
   - **演出家は、返ってきた発話を逐語録に追記する前に、自分の目で2つだけ確かめる。**
     ①まだ語っていない人の台詞を作っていないか
     ②逐語録に無い発言・ト書き・板書を参照していないか。
     当たったらその場で本人に言い直させる。逐語録は共有状態なので、
     放置すると後続の配役が汚染された逐語録を読んで発話する

## 3. テストと転写

1. `test_checklist.md` の手順で逐語録をテストする。
   **テストは、生成した本人とは別のセッション（クリアな目）で行う。**
2. テストの結果、不自然な表現があれば局所修復（他人の台詞の引用は、その人の
   行動の描写に置き換える。対になっている箇所は対で直す）。
   **配役の台詞を演出家が書き換えない。直しは配役本人に言い直させる**
3. **朗読台本に転写する**（手順は `facilitation_guide.md` §6）。
   出力は散文の読み物ではなく、参加者が役を分担して声に出して読む台本。
   要点だけ挙げると——脚本形式（`**話者**「台詞」`）／冒頭にあらすじ・配役表・
   読み方の注記／区切りは「第一幕」／板書はト書きにして黙読させる／
   **タイトルは内容を要約した一行を3候補**
4. **質を記録する**——システム図に書いた膠着が全員の一人称でほどけて
   一つの組織変化として読めるか、シートにもシステム図にも無い発明が起きたか。
   次のケースを作るときに、どこを厚くしてどこを空けるかの材料になる

## 4. レビューする（`templates/review_loop.md`）

最初のシナリオは、整合していても「あなたの現場」の声にはまだなっていない。
シナリオを読んでインラインコメントでレビューし、LLMに反映させる:

1. LLMは指摘箇所を修復する（声を保存して）
2. 同時に、指摘の**傾向**を一般化ルールにして`grounding_notes.md`に
   蓄積し、シート・進行手順・確認項目に反映する
3. 次のrunでは演出家が`grounding_notes.md`を読み込んでから始める

レビューを重ねるほど、ポリフォニーが現場の語彙やふるまいに近づいてくるはず。

## 5. うまくいっているかの見分け方

- 配役が「シートに書いていないこと」を言い出したら、それは成功の兆候
  （核に反していない限り止めない）

## 6. シナリオ生成の際、LLMがよくする失敗

| 症状 | 原因 | 対処 |
|---|---|---|
| 配役が他人の台詞を引用する | 逐語録にない発言への参照か、まだ語っていない人の台詞の創作 | 修復: 台詞引用を「行動ひとつ」に置き換え |
| 行動表明が未来の既成事実になる | 時間軸の混同（帰還後は「現在」） | 現在からの行動に言い直させる |
| 全員が内省的で声が似る | 「あなたの見るくせ・言うくせ」がシートにない | シートに追記して当該ブロックだけ再生成 |
| 物分かりの良い和解が早く来る | シートが厚すぎる | シートを核のみに削る |
